# 윈도우판 설계 (팀용 포크)

- 작성일: 2026-11-13
- 저장소: `likelion-campus/PokeTokenBar` (팀 전용 포크), 기준 `main` c6816f2 (v2.5.629 이후)
- 바탕 문서: [`2026-10-30-team-plaza-design.md`](2026-10-30-team-plaza-design.md) (광장 원칙·안티골).
  이 문서는 "같은 앱을 윈도우에서도 돌린다"만 다룬다. 광장의 놀이 규칙은 바꾸지 않는다.
- 선례: 원본 저장소의 윈도우 포트 PR [chattymin#114](https://github.com/chattymin/PokeTokenBar/pull/114)
  (2026-07, 머지 안 됨, MIT, 브랜치 `WniizMaster/PokeTokenBar:windows-port`). 광장은 없던 시절의 포트다.

표기 규칙: **[결정]** 은 사용자가 대화에서 직접 정한 것, **[설계자 판단]** 은 설계자가 제안했고 사용자가 들은 뒤 받아들인 것,
**[설계자 판단·미확인]** 은 설계자가 정했고 사용자가 아직 보지 못한 것, **[구현자 재량]** 은 구현하면서 정해도 되는 것이다.

## 1. 의도와 이유

같은 사무실 와이파이에 있는 윈도우 팀원이 맥 팀원들과 같은 광장에 들어와 같이 논다 **[결정]**.

- 맥에서 되는 것은 전부 윈도우에서도 된다. 광장뿐 아니라 팝오버(홈·상점·가방·도감·설정)까지다 **[결정]**.
- 새 기능은 맥과 윈도우에 같은 버전으로 같이 나간다 **[결정]**.
- 그래서 광장은 맥과 윈도우가 함께 쓰는 코드 한 벌로 만든다. 지금 잘 도는 맥 광장을 고치는 비용과 위험을 감수한다 **[결정]**.
- 언어는 Swift를 유지한다. 광장 코드는 SpriteKit을 직접 부르지 않고 얇은 그리기 창구를 거친다 **[설계자 판단]**.
- 팝오버만 예외로 윈도우용을 따로 둔다. 원본 업데이트를 받아올 때마다 윈도우 쪽을 맞춘다 **[설계자 판단]**.

Swift를 유지하는 이유 (사용자가 들은 것):
- 광장·팀 테스트 약 2만 7천 줄이 맥 앱의 안전망으로 남는다. (검토에서 고침: 이 중 약 2만 2천 줄은 AppKit·SwiftUI·SpriteKit을
  import해 `PlazaScene`·`PlazaWindowController`를 직접 몬다. 윈도우 CI에서 돌리려면 장면이 창구로 옮겨 갈 때 테스트도
  기록용 구현을 쓰도록 같이 옮겨야 한다. §10의 2~3단계에 포함한다.)
- 맥은 창구 뒤에서 계속 SpriteKit으로 그리므로 맥 팀원이 느낄 변화가 가장 작다.
- 층별로 조금씩 옮길 수 있어, 다른 세션이 광장 기능을 계속 추가하는 중에도 진행할 수 있다.
- 원본 저장소(chattymin) 업데이트를 계속 받아올 수 있다.

## 2. 목표 / 하지 않는 것 / 실패로 보는 것

목표
- G1. 윈도우 10(22H2)·11, x64에서 설치해 실행한다 **[설계자 판단·미확인]** (ARM64는 범위 밖).
- G2. 윈도우 팀원이 같은 팀 코드로, 같은 와이파이의 맥 팀원과 같은 광장에 선다. 통신 형식(`TeamWire`)은 그대로다.
- G3. 광장의 모든 기능이 윈도우에서 맥과 같은 규칙·같은 그림으로 돈다.
- G4. 광장 기능을 새로 만들 때 공용 코드만 고치면 두 OS에 같이 나간다. OS별 코드를 건드려야 하는 경우는
  "새 종류의 그리기 요소"나 "새 OS 서비스"가 필요할 때뿐이다.
- G5. 한 번의 릴리스가 맥 zip과 윈도우 설치 파일을 같은 버전으로 낸다.
- G6. 팝오버의 모든 화면·기능이 윈도우에도 있다.

하지 않는 것
- 다른 네트워크 사이의 광장(보류된 원격 광장). 같은 와이파이만.
- 리눅스.
- 앱 전체를 Tauri·Flutter 등으로 옮기기.
- 원본 저장소에 윈도우 코드를 올리기. 원작자가 #114에서 거절했다. 팀 포크에만 둔다.
- 광장 규칙·맵·그림의 변경.

실패로 보는 것 (기술적으로 돌아가도 실패)
- 맥 팀원의 광장이 느려지거나, 놀고 있을 때 CPU가 눈에 띄게 늘거나, 모습이 달라진다.
- 윈도우판이 맥판보다 한 버전이라도 늦게 나가는 일이 되풀이된다.
- 광장 기능 하나를 만들 때마다 윈도우용 코드를 따로 써야 한다.
- 윈도우 팀원이 광장에 들어오려고 관리자 권한 설정이나 별도 프로그램(Bonjour 등) 설치를 해야 한다.

## 3. 지금 상태 (조사 결과)

`main` c6816f2 기준, Swift 160파일 약 4만 6천 줄.

| 구분 | 분량 | 윈도우에서 |
|---|---|---|
| Foundation만 쓰는 로직 (`Core` 1만 1천, `Team` 3천) | 약 1만 4천 줄 | 그대로 컴파일될 것으로 본다 |
| OS 서비스를 부르는 코드 (Security, Network, UserNotifications, ServiceManagement, CryptoKit, Darwin) | 약 5천 줄 | 부르는 곳만 갈아 끼운다 |
| `Team` 중 CoreGraphics만 import | 약 3천 줄 | 좌표 타입만 쓰는 약 1천 8백 줄은 Foundation의 `CGPoint` 등으로 해결될 것으로 본다. 나머지 약 1천 2백 줄(`PlazaTileArt`, `CampfireArt`, `TallGrassArt`, `NestArt`, `SnowSheet`, `GroundShadow`, `Weather`, `PhotoRenderer`)은 `CGContext`·`CGImage`로 그림을 만든다. 윈도우에 없으므로 §5의 "그림 만들기"로 옮긴다 |
| 광장 그리기 (SpriteKit 10파일) | 약 6천 줄 | 창구로 옮긴다 (§5) |
| 광장 위 화면 (SwiftUI, `Team/UI`) | 약 2천 줄 | 창구로 옮긴다 (§6) |
| 팝오버·펫 (`UI`, SwiftUI/AppKit) | 약 9천 줄 | 윈도우용을 따로 만든다 (§8) |

알아 둘 사실
- 광장이 쓰는 SpriteKit 종류는 적다: `SKSpriteNode`(67곳), `SKTexture`(47), `SKView`(8), `SKNode`(7),
  `SKCameraNode`(2), `SKCropNode`(1), `SKScene`(1). `SKAction`, `SKLabelNode`, `SKEmitterNode`는 쓰지 않는다.
  움직임은 프레임마다 코드가 직접 계산하고, 글자는 CoreText로 그림을 만들어 텍스처로 올린다.
- 이름표는 Galmuri가 아니라 맥 시스템 글꼴(굵게)을 쓰고, 말풍선의 이모지는 Apple Color Emoji로 그린다.
- 캐릭터는 움직이는 GIF다. 원본 소유 디렉터리의 `UI/SpriteLoader`·`GIFDecoder`(AppKit `NSImage`)로 읽는다.
- 기능 로직의 대부분(키, 몸통박치기, 눈덩이, 메타몽, 사진, 집중, 팀원 동기화)은 `PlazaWindowController.swift`
  (2,163줄, AppKit+SpriteKit)에 있다.
- 팀 연결은 이미 `TeamTransporting` 프로토콜 뒤에 있다. 맥 구현은 `BonjourTeamTransport`
  (서비스 `_ptbteam._tcp`, TLS 1.2, `TLS_PSK_WITH_AES_128_GCM_SHA256`, 키는 팀 코드에서 유도).
- 광장 리소스는 PNG 2장과 Galmuri 글꼴 2개다. 포켓몬 그림은 실행 중에 PokéAPI에서 받아 캐시한다.
- SQLite는 맥에서 시스템 라이브러리를 쓴다. 윈도우 Swift에는 없어서 #114는 공개 도메인 소스를 넣었다.
- Claude 로그인 정보는 이미 키체인 없이 `~/.claude/.credentials.json`에서 읽는 길이 있다.
- 10월 이후 변경 횟수: `Team` 79, `Core` 55, `UI` 43(그중 26이 원본에서 옴). 광장은 거의 매일 바뀐다.

## 4. 전체 구조

모듈은 지금처럼 하나로 두고, 파일을 세 묶음으로 나눈다 **[설계자 판단·미확인]**. (검토에서 고침: 처음엔 SwiftPM 타깃을
여럿으로 나누려 했다. 그러면 원본이 소유한 `Core`의 심벌마다 `public`을 붙여야 해서 원본 동기화 때마다 충돌한다.)

```
공용        사용량·컴패니언·팀 통신·광장 규칙·광장 장면·광장 위 화면. 두 OS에서 컴파일한다.
            AppKit/SwiftUI/SpriteKit/CoreText/ImageIO 등 import 금지. 그리기는 창구(§5), OS 일은 서비스 프로토콜(§7)로.
맥 전용     메뉴바, SwiftUI 팝오버, SpriteKit 그리기 부품, 맥 OS 서비스. 윈도우 빌드에서 제외.
윈도우 전용 트레이, 윈도우 팝오버, Direct2D 그리기 부품, 윈도우 OS 서비스. 맥 빌드에서 제외.
```

`Package.swift`가 OS에 따라 전용 파일 묶음을 `exclude`한다. 묶음은 디렉터리로 구분한다(이름은 **[구현자 재량]**).
원본 소유 파일 중 AppKit·UserNotifications를 부르는 넷(`UsageStore`, `CompanionStore`, `UpdateChecker`,
`CrashReporter`)은 그 호출을 서비스 프로토콜로 바꾸는 최소 수정만 한다. 원본과 벌어지는 줄을 PR마다 적는다.

- 공용 묶음의 파일이 금지된 프레임워크를 import하면 실패하는 검사 테스트를 둔다(`TestDefaults` 검사 테스트와 같은 방식).
  G4를 사람의 주의가 아니라 기계로 지킨다.
- 파일을 옮기는 일은 원본 동기화와 충돌한다. `Core`·`UI`는 원본이 계속 바꾸므로 **위치를 옮기지 않는다.**
  팀 포크만 가진 `Team`은 자유롭게 옮겨도 된다 **[설계자 판단·미확인]**.
- OS별 분기는 `#if os()`를 공용 코드에 흩뿌리지 않고 서비스 프로토콜 구현으로 모은다. 원작자가 #114를
  거절한 이유(숨은 `#if os()` 두 벌)를 되풀이하지 않는다.

## 5. 그리기 창구

광장 장면 코드가 쓰는 유일한 그리기 수단이다. SpriteKit에서 실제로 쓰는 것만 담는다.

담는 것 (이름은 **[구현자 재량]**)
- 노드: 위치, z 순서, 투명도, 숨김, 크기 배율, 자식 목록.
- 스프라이트 노드: 텍스처, 크기, 기준점, 색 섞기, 좌우 뒤집기. 확대는 항상 최근접(픽셀 아트).
- 텍스처: PNG 바이트나 RGBA 픽셀에서 만들기, 부분 영역 잘라 쓰기.
- 잘라내기 노드(`SKCropNode` 한 곳에 해당)와 카메라(위치, 배율).
- 회전(`zRotation`, 춤 기울임)과 섞기 방식(`.multiply` 낮밤, `.multiplyX2` 모닥불 빛·불꽃놀이).
- 움직이는 GIF를 프레임별 RGBA로 푸는 디코더. 공용 코드로 두고 맥의 `UI/SpriteLoader`와 결과가 같은지 테스트로 맞춘다.
- 사진: 창 없이 장면을 RGBA로 그려 PNG로 내보내기, 클립보드에 그림 넣기(클립보드는 §7의 OS 서비스).
- 화면: 프레임 콜백(경과 시간), 일시정지, 보이는 영역, 장면 좌표 ↔ 화면 좌표 변환.
- 입력: 키 누름·뗌(물리 키 기준), 마우스 클릭·이동·휠. OS 이벤트를 공용 입력 타입으로 바꿔 넘긴다.
- 그림 만들기: 글자(Galmuri 11/14, 한글 포함)와 둥근 사각형·선·채움으로 RGBA 그림을 만든다.
  이름표·말풍선·이모트·광장 위 화면이 모두 이것을 쓴다.

구현
- 맥: SpriteKit에 1:1로 대응한다. 그림 만들기는 지금의 CoreGraphics/CoreText 코드를 그대로 쓴다.
  맥에서 화면에 나오는 결과는 옮기기 전과 픽셀 단위로 같아야 한다.
- 윈도우: Direct2D(그리기)·DirectWrite(글자)·WIC(PNG) **[설계자 판단·미확인]**. 모두 윈도우 기본 탑재라
  따로 배포할 것이 없다. Swift에서 COM을 부르는 얇은 C/C++ 보조 타깃이 필요할 수 있다 **[구현자 재량]**.
- 테스트용: 아무것도 그리지 않고 노드 트리만 기록하는 구현. 공용 광장 테스트는 이것으로 두 OS에서 돈다.

글자가 맥과 윈도우에서 픽셀까지 같지는 않을 수 있다(글자 그리는 엔진이 다르다). Galmuri는 비트맵풍 글꼴이라
정수 크기·안티에일리어싱 끔으로 맞추는 것을 목표로 하되, 한두 픽셀 차이는 허용한다 **[설계자 판단·미확인]**.

이름표와 이모지는 다르다. 맥은 시스템 글꼴과 Apple Color Emoji를 쓰는데 둘 다 윈도우에 없다. 윈도우에서는
맑은 고딕(굵게)과 Segoe UI Emoji를 쓴다. 글자 모양이 맥과 다르게 보인다. 두 OS에 같은 글꼴을 넣어 맞추면 맥의 모습이
바뀌므로(§2의 실패 조건) 하지 않는다 **[설계자 판단·미확인]**.

## 6. 광장 위 화면 (채팅·명단·카드·메뉴·미니맵·시계·단축키 안내)

지금은 SwiftUI 뷰(`Team/UI`, 약 2천 줄)다. 광장 기능과 함께 자주 바뀌므로 한 벌이어야 한다.

- §5의 창구로 그린다. 배치는 공용 코드가 계산하고, 글자와 패널은 "그림 만들기"로 만든다 **[설계자 판단·미확인]**.
- 예외는 채팅 입력 칸 하나다. 한글 입력기(IME) 조합을 직접 구현하지 않는다. OS 기본 입력창(맥 `NSTextField`,
  윈도우 `EDIT` 컨트롤)을 광장 창 위에 얹고, 공용 코드는 "입력창을 이 자리에 보여라 / 글이 확정됐다"만 주고받는다.
- 마우스 올림·클릭 판정(명단 칸, 메뉴 항목)은 공용 코드가 한다.
- 이 화면들은 맥에서 SwiftUI일 때와 모양이 조금 달라질 수 있다. 옮기기 전후 그림을 PR에 붙여 사용자가 본다.

## 7. OS 서비스

프로토콜로 두고 OS별로 구현한다.

| 서비스 | 맥 (지금) | 윈도우 |
|---|---|---|
| 팀 찾기 | `NWBrowser`/`NWListener` Bonjour | 윈도우 기본 DNS-SD (`DnsServiceBrowse`/`DnsServiceRegister`, Win10+) |
| 팀 연결 암호화 | Network.framework TLS-PSK | §9 실험으로 정한다: Schannel PSK 또는 앱에 넣은 TLS 라이브러리 |
| 비밀 보관 | Keychain | Windows Credential Manager 또는 DPAPI **[구현자 재량]** |
| 해시·암호 | CryptoKit | swift-crypto (같은 API) |
| 알림 | UserNotifications | 윈도우 토스트 알림 |
| 로그인 시 자동 실행 | ServiceManagement | 레지스트리 Run 키 (#114 방식) |
| 잠자기·깨어남·화면 꺼짐 | `NSWorkspace` 알림 | `WM_POWERBROADCAST` 등 |
| 네트워크 연결 상태 | `NWPathMonitor` | 윈도우 네트워크 상태 API |
| 클립보드에 그림 넣기 (사진) | `NSPasteboard` | 윈도우 클립보드 |
| 중복 실행 방지 | 지금 구현 | 이름 있는 뮤텍스 (#114 방식) |
| SQLite | 시스템 라이브러리 | 공개 도메인 소스를 타깃으로 넣는다 (#114 방식) |
| 외부 도구 로그 위치 | `~/Library/Application Support/…` 등 | 도구별 윈도우 경로. 프로바이더 루트 목록에만 더한다 (`provider-extension.md` 규약) |
| 업데이트 확인·설치 | GitHub 릴리스 + brew | GitHub 릴리스 + 설치 파일 |

통신 호환
- 윈도우 구현은 맥의 `BonjourTeamTransport`와 선 위에서 같아야 한다: 같은 서비스 이름, 같은 PSK 유도,
  같은 암호 스위트, 같은 프레임 형식. 프로토콜 버전을 올리지 않는다.
- 윈도우 방화벽: 처음 실행 때 "개인 네트워크 허용" 창이 뜬다. 설치 파일이 방화벽 규칙을 미리 넣을지는
  §9 실험 뒤에 정한다 **[구현자 재량]**. 관리자 권한을 요구하게 되면 사용자에게 먼저 알린다.

## 8. 팝오버 (예외: 두 벌)

- 맥은 지금의 SwiftUI를 그대로 둔다. 원본 변경을 그대로 받는다.
- 윈도우는 같은 화면을 윈도우용으로 만든다. 로직(`UsageStore`, `CompanionStore`, 현지화 문자열)은 공용을 쓴다.
- 기능은 전부 같게, 모양은 윈도우 기본 버튼·입력칸·목록(Win32 기본 컨트롤)으로 만든다. 맥과 생김새가 다른 것을
  받아들인다 **[설계자 판단]**. 맥과 똑같이 직접 그리는 안은 화면 9천 줄 분량의 UI 도구를 만드는 일이라 버렸다.
  포켓몬 그림·그래프처럼 기본 컨트롤로 안 되는 부분만 §5의 "그림 만들기"로 그린다.
  #114의 Win32/GDI 코드(1,743줄)를 화면 구성과 트레이 처리의 출발점으로 삼는다. SwiftCrossUI는 아직 실험 단계라 쓰지 않는다.
- 메뉴바 아이콘은 트레이 아이콘이 된다. 트레이는 글자를 붙일 수 없으므로 숫자는 아이콘 툴팁과 팝오버에서 본다.
  윈도우 11은 새 트레이 아이콘을 숨김 영역에 두므로, 첫 실행 때 꺼내는 방법을 안내한다.
- 떠다니는 펫(`FloatingPetPanel`)도 "전부 다"에 포함된다. 윈도우에서는 항상 위에 뜨는 테두리 없는 창으로 만든다.
- 맞춤 유지: 원본 동기화 PR마다 "팝오버에서 바뀐 것 → 윈도우 쪽 반영" 목록을 PR 본문에 적는다.
  새 검사를 만들어, 현지화 키·설정 항목 중 윈도우 화면이 쓰지 않는 것이 있으면 실패하게 한다 **[설계자 판단·미확인]**.
  (`scripts/parity-check.sh`는 토큰 합계를 ccusage와 비교하는 다른 도구라 쓰지 않는다.)

## 9. 먼저 하는 실험 (버리는 코드)

아래 넷은 계획을 세우기 전에 답이 필요하다. 각각 작은 버리는 코드로 확인하고, 결과를 이 문서에 적는다.
실험 코드는 `main`에 넣지 않는다.

1. **공용 로직이 윈도우에서 컴파일되고 테스트가 도는가.** GitHub Actions 윈도우 러너에서 `Core`와 `Team`의
   Foundation-only 부분을 빌드하고 테스트한다. 막히는 API 목록을 얻는다.
2. **맥과 윈도우가 서로 찾고 연결되는가.** 윈도우에서 `_ptbteam._tcp`를 알리고 찾고, 맥의 지금 앱과 TLS-PSK로
   프레임을 주고받는 최소 프로그램. Schannel의 PSK가 관리자 설정 없이 되는지 본다. 안 되면 PSK를 지원하는
   TLS 라이브러리(예: BoringSSL 계열)를 넣는 방법으로 다시 한다. **실제 윈도우 PC와 사무실 와이파이가 필요하다.**
3. **Swift에서 Direct2D 창을 띄워 픽셀 아트와 Galmuri 한글을 그릴 수 있는가.** 광장 타일과 이름표 하나를
   그려 PNG로 저장한다. CI 윈도우 러너에서 창 없이(소프트웨어 렌더러) 그림을 뽑을 수 있는지도 본다.
   이것이 되어야 맥에서 작업하는 세션이 윈도우 화면을 확인할 수 있다.
4. **창구를 거친 맥 광장이 지금과 같은가.** `PlazaPondLayer` 같은 작은 층 하나를 창구로 옮겨, 화면 밖 렌더
   결과가 옮기기 전과 픽셀 단위로 같고 프레임 시간이 늘지 않는지 본다.

넷 중 하나라도 "안 된다"로 끝나면 이 설계로 돌아와 고친다. 특히 2가 막히면 통신 방식 자체를 다시 정해야 하고,
그것은 맥 쪽 프로토콜 변경이 될 수 있으므로 사용자에게 먼저 묻는다.

## 10. 순서

각 단계는 그 자체로 `main`에 들어가도 맥 앱이 정상이어야 한다. 맥 릴리스는 평소대로 계속 나간다.

0. §9 실험 넷. 결과로 이 문서를 고친다.
1. 타깃 나누기와 금지 import 검사. 윈도우 CI 러너에서 공용 타깃 빌드·테스트. (윈도우 앱은 아직 없다.)
2. 그리기 창구 + 맥 SpriteKit 구현. 광장 층을 하나씩 옮긴다(작은 층 → `PlazaActor` → `PlazaScene`).
   PR마다 화면 밖 렌더로 전후가 같음을 보인다.
3. 광장 위 화면을 창구로 옮긴다(채팅 입력 칸 예외 포함). `PlazaWindowController`를 둘로 가른다: 기능 로직(키, 몸통박치기,
   눈덩이, 메타몽, 사진, 집중, 팀원 동기화)은 공용으로, 창·이벤트 받기는 맥 전용의 얇은 껍데기로. 이것이 옮겨지지 않으면
   G4가 성립하지 않는다. 이 컨트롤러와 장면을 직접 모는 테스트도 기록용 구현을 쓰도록 같이 옮긴다. 여기까지가 맥 쪽 재작업이다.
   **이 시점부터 새 광장 기능은 공용 타깃에만 쓴다.**
4. 윈도우 뼈대: 트레이, OS 서비스 구현, 사용량·컴패니언이 도는 최소 앱. 설치 파일.
5. 윈도우 팀 연결. 맥 팀원과 서로 보인다(명단·알림까지).
6. 윈도우 그리기 구현과 광장 창. 맥 팀원과 같은 광장에 선다.
7. 윈도우 팝오버 전체, 떠다니는 펫.
8. 릴리스 통합: 한 번에 두 OS 산출물, 윈도우 게이트, 문서·랜딩.

2~3과 4~5는 서로 독립이라 다른 세션이 나란히 할 수 있다.

진행 중에 다른 세션이 광장 기능을 추가한다. 2~3 동안에는 "이미 옮긴 층에는 창구로만 쓴다"를 금지 import 검사가
층 단위로 강제한다(옮긴 파일 목록을 검사에 더해 간다).

## 11. 확인 방법

- 공용 테스트(광장 규칙·장면·통신)는 맥과 윈도우 CI 양쪽에서 돈다.
- 윈도우 CI는 PR 머지를 막지 않는다. 지금처럼 기다리지 않고 머지하고, 깨지면 바로 고친다. 대신 윈도우 빌드·테스트가
  깨져 있으면 릴리스가 나가지 않는다. 그동안 맥 배포도 같이 멈춘다 **[설계자 판단]**.
- 윈도우 화면: CI 윈도우 러너가 창 없이 그린 PNG를 산출물로 올리고, 맥에서 그린 같은 장면과 나란히 비교한다.
  PR의 `UI changes`에는 두 OS 그림을 함께 붙인다.
- 통신 호환: 맥 구현과 윈도우 구현이 같은 바이트를 내는지 보는 테스트(PSK 유도, 프레임). 실제 맥↔윈도우
  연결은 사람이 윈도우 PC에서 확인한다. `scripts/team-probe.swift`에 해당하는 윈도우용 점검 도구를 둔다.
- 맥 회귀: 창구로 옮기는 PR마다 화면 밖 렌더 전후 비교와 프레임 시간 측정.
- 결함이 나오면 `CLAUDE.md`의 결함 대응 프로토콜을 따른다. "맥에서만 확인하고 윈도우에서 깨진" 부류는
  `defect-log.md`에 새 항목으로 쌓는다.

윈도우 PC 확인은 사용자가 PC를 구해 직접 한다 **[결정]**. 매 PR이 아니라 단계가 끝날 때(§9 실험 2, §10의 4~8 각 단계)
확인을 부탁한다 **[설계자 판단·미확인]**. 그 사이는 CI 그림과 테스트로 버틴다.

한계: 이 작업을 하는 세션은 맥에서 돈다. 윈도우에서 직접 실행해 볼 수 없으므로, 실제 사용감(트레이, 입력기,
방화벽 창, 설치)은 윈도우 PC를 가진 사람의 확인에 기댄다.

## 12. 배포

- 윈도우 빌드는 GitHub Actions 윈도우 러너에서 만든다(맥에서 교차 빌드하지 않는다).
- 설치 파일: 사용자별 설치(관리자 권한 없음), 시작 메뉴 등록, 제거 항목. 도구는 Inno Setup(#114 방식) **[구현자 재량]**.
- 코드 서명 인증서가 없으면 설치 때 "알 수 없는 게시자" 경고(SmartScreen)가 뜬다. 팀 내부 배포이므로
  처음에는 서명 없이 내고 경고 넘기는 법을 안내한다 **[설계자 판단·미확인]**. 인증서 구입은 사용자 결정이다.
- 지금 `team-release.sh`는 태그와 릴리스를 한 번에 만든다. 순서를 바꾼다: 버전 올린 커밋에서 윈도우 워크플로가 설치 파일을
  먼저 만들고 게이트를 통과한 뒤에, 스크립트가 맥 zip과 그 설치 파일을 함께 붙여 릴리스를 만든다.
  두 OS 중 하나라도 게이트가 실패하면 릴리스하지 않는다. 그래야 "같은 버전으로 같이"가 지켜진다.
  릴리스 한 번이 윈도우 빌드 시간만큼 길어진다.
- 윈도우 업데이트: 앱이 새 릴리스를 알리고 설치 파일을 받아 실행한다. winget 등록은 범위 밖.
- 릴리스 노트는 지금 형식을 유지하고 Install / Upgrade에 윈도우 절을 더한다.
